02Executive Summary

The design session produced a coherent, opinionated visual language that the current code partly anticipated and partly does not yet accommodate. There is no incompatibility that requires a rewrite, but there are several places where stale or contradictory wiring will quietly bite if integration begins without a deliberate pass.

What lines up cleanly

Six of the design's named themes (solar-plasma, obsidian-aurora, midnight-loom, void-circuit, agartha-dream, agartha-dusk) match the existing ThemeId union exactly. The NodeSphereProgram already wired into Sigma at SigmaGraphView.tsx:510 implements roughly half of what the design's GlassSphere shows — radial alpha, Phong specular, glow falloff, rim light. The themeTargetRegistry + data-lw-theme-target attribute system is the perfect anchor for the design's Alt+Shift+click radial menu, with the existing canonical-token validation in themeOverrideStorage and themeTokenGovernance ready to receive whatever the radial menu writes back.

What does not line up

Two empty .ts/.tsx files sit in the tree (tokens.ts and DockLayout.tsx) — both legitimate-looking placeholders that no longer have content. The panel-registry.ts file describes seven panels (sources, lenses, inspector, evidence, physics, logs, qa) that do not match what AppShell.tsx actually mounts; this registry is stale and will mislead any tile-system rewrite that consults it. The Solar Plasma palette in code is cooler than the design's warm cream-and-gold treatment — a deliberate choice of consequence. The Settings tab the design asked to remove is still hardcoded into LeftTabPanel's tab list. And the design's tile system is fundamentally per-section while the current code's tile system is per-whole-tab; reconciling the two is a real piece of work, not a rename.

Reply "go" and I'll start Milestone A in a fresh turn. — Claude Design, log entry before the build began

Three milestones (A — visual fixes, B — tile system, C — inspector overlay) shipped before the design session paused at 77% of its weekly limit. Milestone D (theme lifecycle) and E (3D minimap + audio reactivity) were never started. The eight files in this review represent A + B + the very beginning of C.

03Critical Findings

These are the items that will cause silent failure or wasted work if integration begins without addressing them. Each is described in enough detail that Bandit can act on it without re-deriving the context.

Two zero-byte source files in the tree

v86a Critical
tokens.ts · DockLayout.tsx

Both files are present at zero bytes. Neither has any importer in the codebase based on a full grep across all .ts/.tsx files — the theme system has already migrated to themeTokens.ts, theme.types.ts, themeTokenPaths.ts, and themeTargetRegistry.ts, none of which need tokens.ts; and nothing references DockLayout as a component.

The risk is not that they will break a build today — TypeScript tolerates empty modules and the dead exports are simply unreachable. The risk is that during integration, someone (Claude Design did this in conversation) will read the filename, assume the file is the home of a feature, and either mis-place new code there or build around an absent contract that they expect the file to honor.

  • tokens.ts — almost certainly a leftover from a token-system refactor. The exports it would have held are now distributed across theme.types.ts (the ThemeRuntimeTokens interface), themeTokens.ts (the per-theme token values), and themeTokenPaths.ts (the canonical path enumeration).
  • DockLayout.tsx — name suggests a layout primitive; panel-registry.ts mentions zones left | right | bottom that imply a dock, but no component actually consumes the registry. This is probably where the dock layout was meant to live before the sidebar split into LeftTabPanel and ControlDock.
Action Delete both files, or write a one-line comment header explaining why they are empty placeholders, before any tile-system rewrite begins. Resolve the question of whether panel-registry.ts should also be removed at the same time (see Finding 2).

panel-registry.ts is stale and contradicts the actual UI

v86a Critical
panel-registry.ts · panel.types.ts

The panel registry declares seven panels — sources, lenses, inspector, evidence, physics, logs, qa — distributed across three zones (left, right, bottom). The actual UI mounts none of these names. AppShell.tsx assembles its left side from the five hardcoded tabs in LeftTabPanel (graph, qa, evidence, debug, settings) and its right side from ControlDock, which currently just renders SettingsPanel directly. There is no bottom zone in use, and there is no lenses or sources panel anywhere.

This matters because the design's tile system is exactly the kind of feature that would naturally consume a panel registry. If integration begins by wiring tile tear-off through panelRegistry, every tile will be addressing ghost panels that the rest of the app does not render, and tile state will desynchronize from the actual UI. If integration ignores the registry, two parallel tile-addressing systems will then exist forever.

Decision Either rewrite panel-registry.ts to mirror what AppShell.tsx actually mounts and have AppShell consume it as the source of truth, or delete the registry entirely and let the design's TileProvider own the panel taxonomy. I recommend the first: a registry is the right home for "which panels can be torn off, which start collapsed, which are gated by feature flag." It just needs to be true.

The Settings tab the design dropped is still wired in

v86a Conflict
LeftTabPanel.tsx · settings.schema.ts · AppShell.tsx

One of the user's first directives in the design conversation was to remove the Settings tab from the left panel because the same controls had migrated to the right-side Control Dock. _NEW_shell.jsx reflects this — its LEFT_TABS array contains exactly four entries (graph, qa, evidence, debug). The current LeftTabPanel.tsx hardcodes five tabs in three places that all need to move together:

  • The tabs array at lines 65–71 — adds settings as the fifth entry.
  • TAB_ICONS at lines 58–63 — only has icons for the first four, so the Settings tab already falls back to its label's first letter ("S"). Someone has been quietly de-emphasizing this tab.
  • The activeTab prop type at line 7 — typed as "graph" | "qa" | "evidence" | "debug" | "settings".

Three further locations propagate the same union: the StarmapSettings.ui.leftPanelActiveTab type in settings.schema.ts, the settingsTabSections sub-object in the same file, and the tiledTabs array which can contain "settings". Removing the tab without fixing all three will leave dangling references that compile but do nothing.

Action Coordinate the tab removal as a single change: delete from LeftTabPanel's tab list, narrow the leftPanelActiveTab union, drop the settingsTabSections object from the schema, and write a settings migration that rewrites stored leftPanelActiveTab: "settings" values to "graph" on load. Run the existing theme-target-inspector.spec.ts and app-smoke.spec.ts to make sure nothing in the test suite still asserts the fifth tab is present.

Solar Plasma in code is cool; Solar Plasma in design is warm

v86a Conflict
themeTokens.solarPlasmaTokens vs. _NEW_graph-data.SP

Both surfaces carry the name "Solar Plasma" but their palettes are emotionally different paintings. Current code reads as a cool slate-and-cyan dashboard: app.background is #020617 (slate-950), textPrimary is #f1f5f9 (slate-100), panelBorder is cyan at 20% alpha. The design treatment in _NEW_graph-data.jsx reads as a warm, cinematic, deep-purple-with-gold treatment: voidDeep #03000A as background, ink #FFE9D6 (warm cream) as text, goldBorder rgba(255, 179, 71, 0.32) as panel border.

The graph node colors mostly align — coronaCyan, flareGold, flareOrange, fuchsia, purple all have direct counterparts in nodeColorScale. But the chrome — the shell, the panel surfaces, the text — is a different aesthetic. The screenshots from the brand exploration (warm cream wordmark, gold accents, purple voids) confirm the design's intent.

Decision Choose one of two paths. Path A: overwrite the chrome side of solarPlasmaTokens with the warm palette and accept that current users see a visual change next release. Path B: add a new preset (e.g. solar-plasma-warm or rename the current one to solar-plasma-cool and let the warm treatment own the original name). Path A is what the design conversation implies; Path B is safer for any external screenshots or documentation that reference the current look.

Inspector trigger collision: Alt+Shift+I vs. Alt+Shift+click

v86d Conflict
ThemeTargetInspectorOverlay.tsx · _NEW_inspector-overlay.jsx

Current code uses Alt+Shift+I as a toggle that enables a hover-discovery mode over [data-lw-theme-target] elements, plus Alt+Shift+P to pin the currently-hovered entity. The design's inspector overlay uses Alt+Shift+click on a target to summon a radial menu for editing it. These do not conflict at the keypress level — one is a chord toggle, the other is a chord-modified click — but they use overlapping visual real estate (both draw ghost halos around theme targets) and the user will form a single mental model of "the Alt+Shift inspector," not two.

Treat them as one feature with two triggers, not two features. The current overlay's strength is discovery: it highlights every registered target and surfaces warning badges for inferred candidates the registry has not yet annotated. The design's overlay's strength is mutation: it lets the user change a target's color, geometry, motion, and so on, with a scope picker that determines whether the change applies to this one element, all of its kind, the cluster, or everything.

Action Keep the existing overlay as the discovery layer. Add the radial menu as a second mode that activates on Alt+Shift+click while the discovery layer is enabled, or on Alt+Shift+click anywhere if a separate kill switch is preferred. Wire the radial menu's "apply" actions through themeOverrideStorage.applyOverride so changes persist via the existing canonical-token-validation pipeline rather than a parallel one. The design's mock'd inspector:apply CustomEvent dispatch is the integration seam.

themeOverrideStorage is global-only; the design's scope picker demands per-target scoping

v86a + v86d Conflict
themeOverrideStorage.ts (v34a)

The header comment in themeOverrideStorage.ts reads "Global-only theme override storage foundation. Validates against canonical ThemeTokenPath values only. Rejects planned/noncanonical token paths. Base presets remain immutable." The storage records each override as { tokenPath, value, timestamp }. There is no target-id, no kind, no cluster.

The design's radial menu has a four-step scope picker: this (single element), kind (all elements of this kind), cluster (the BFS-walked selection group), global (the whole theme). Only the last of those four is expressible in the current schema. The other three need a new shape, something like: 

interface ScopedThemeOverride {
  tokenPath: ThemeTokenPath;
  value: ThemeTokenValue;
  timestamp: number;
  scope: {
    kind: "global" | "target" | "target-kind" | "cluster";
    targetId?: string;       // for "target"
    targetKind?: string;     // for "target-kind"
    clusterAnchor?: string;  // for "cluster" — node id used as BFS root
  };
}

The schema migration here is the pivot point for the entire radial-menu feature. Until themeOverrideStorage understands scope, "Apply to similar" and "Apply to cluster" can only be live-preview, never persisted.

Decision Schedule the scoped-overrides migration as a prerequisite for the radial-menu work, not as part of it. Two phases: first add the scope field with default { kind: "global" } (existing data migrates cleanly); then build the radial menu on top of the scoped storage. Resist the temptation to do both in one PR — the storage shape change touches Playwright tests (theme-override-storage.spec.ts) that are easier to reason about in isolation.

Tile granularity: per-tab in code, per-section in design

v86c Conflict
Tile.tsx · settings.ui.tiledTabs · _NEW_tile-system.jsx

Current code lets the user tear off an entire tab into a tile via the small ⬚ icon in LeftTabPanel. The torn-off tab id lands in settings.ui.tiledTabs: Array<TabId> and AppShell renders a Tile for each one outside the grid. The Tile component supports free-floating drag and 8-handle resize, but no snap, no grouping, no edge magnetism, and no concept of "this tile came from inside that other panel section."

The design works at section granularity: every accordion section in the left panel and every dock section in the right panel grows a ⤴ tear-off handle, and dragging it converts that one section into a floating tile while the original slot greys out and pulses with a "Tiled out" label. Tiles snap to a 16-pixel grid and edge-magnetize within 22 pixels; two snapped tiles automatically form a group with a shared header bar that hugs the rectilinear hull of the arrangement (the user's "BIG RULE" — the bar's width matches only the topmost row, not the bounding box of the group).

Reconciling these is not a cosmetic change. The state shape Array<TabId> cannot represent torn-off sections within tabs, nor groups of sections, nor snap positions, nor collapse state per tile within a group. The whole tile-state model is wrong for the design.

Action Replace tiledTabs: Array<TabId> with a richer shape, suggested below. Keep the old field one release for migration, then drop it. Build the TileProvider context from the design as the new owner; Tile.tsx's drag/resize logic can be reused inside FloatingTile but the snap/group machinery is genuinely new code. 
interface TileLayoutEntry {
  id: string;                         // "tile_xyz"
  sectionKey: string;                  // "graphSources" | "physics" | …
  x: number; y: number;             // snapped 16-pt grid
  w: number; h: number;
  collapsed: boolean;
  z: number;                          // stacking order
  groupId?: string;                    // computed at runtime, not stored
}

// settings.ui
tiledTabs: Array<TabId>;                          // REMOVE
tileLayout: TileLayoutEntry[];                    // REPLACE

Two renderers want to coexist: WebGL Sigma vs. hand-rolled SVG

v86b Conflict
SigmaGraphView.tsx · _NEW_graph-view.jsx

SigmaGraphView is a real production renderer built on Graphology and Sigma with FA2 layout running in a worker. It already integrates a custom node program (NodeSphereProgram) and label-policy machinery (applyGraphLabelPolicyToGraphology, graphStylePolicy) and runs against the normalized graph from useGraphSourceSummary.

_NEW_graph-view.jsx is a hand-rolled SVG renderer with custom camera projection, easing, rotation, click halos, glitter fields, plasma-stream edges with animated particles, floating bookmarks, and an interactive minimap. It targets the synthetic 110-node fixture and assumes nothing about Sigma.

The design intends nearly all of these visual treatments to apply to the real graph. Sigma's WebGL renderer is faster and already wired; rebuilding the production graph in SVG would be a regression for any nontrivial dataset. So the integration question is: which design features are shader / node-program work (extend Sigma) and which are overlay work (an SVG layer on top of Sigma's canvas).

  • Shader / node-program work: the glass-sphere interior flow, hum, glow strength — these need new uniforms on NodeSphereProgram (or a successor program) that sample nodeHum, nodeFlowSpeed, nodeGlow from JavaScript per frame. The PlasmaEdge treatment requires an EdgeProgram extension.
  • Overlay work: click halo, glitter field, floating bookmarks, minimap, camera HUD, draggable inspector. None of these need to live in WebGL — they sit in an absolutely-positioned overlay div above the Sigma canvas and read camera state via Sigma's API.
  • Background work: SolarBackdrop (corona, flares, field lines, starfield, vignette) is purely behind the canvas — a CSS-and-SVG layer with no graph data dependency.
Decision Do not port _NEW_graph-view.jsx as a renderer. Treat it as a visual specification and re-implement each piece in its correct architectural slot: shader uniforms, absolute-positioned overlay components, or pure CSS background. The design's custom camera projection (left-pan, right-rotate, scroll-zoom) maps onto Sigma's camera with a small wrapper.

06Tile System Conflicts

The tile system is the place where design and code disagree most fundamentally. Worth its own section because the granularity change ripples into settings, into the panel registry, and into every section accordion in the left and right panels.

The granularity gap

Reading the design conversation, the user is explicit that they want sections — not tabs — to be the unit of tile-out. The argument is that a Settings tab full of Physics, Labels, Theme, and Inspector accordions is not a useful tile; the user wants to tear off just the Physics accordion to a corner of the screen while continuing to work in the rest of Settings. The design's TileableSection wraps every accordion with a ⤴ handle that makes that possible.

Why the panel-registry decision matters here

The design's TileProvider takes a registry prop with shape { [sectionKey]: { title, content, originPanel } } — each entry tells the tile system how to render the section as a tile and which panel it came from (so the source slot can grey out). This registry could absolutely be sourced from a rationalized panel-registry.ts. If the registry question (Critical Finding 2) is resolved in the same change set, the tile registry becomes a derived view of the panel registry — no parallel taxonomy.

The fusion plan

The two overlays have non-overlapping value. Treat them as one feature with two phases of interaction:

  1. Discovery phase — Alt+Shift+I activates the existing overlay. Ghost outlines appear on every registered and inferred theme target. The user sees what is themable.
  2. Mutation phase — Alt+Shift+click on any highlighted target (or, if discovery is off, on any element that carries data-lw-theme-target) summons the design's radial menu. The clicked target's themeTargetId flows into the popover as the edit subject.

The mutation phase needs three things from the rest of the system:

  • A persistence path. The radial menu's this-scoped color edit needs to write into themeOverrideStorage with the new scope: { kind: "target", targetId } field (Conflict 4). The global scope is already supported.
  • An eyedropper source. The hover-preview eyedropper needs to read pixel values from the screen. The EyeDropper API (window.EyeDropper) is the path where browser support exists; otherwise fall back to clicking rendered elements and reading getComputedStyle.
  • An apply-to-similar oracle. The ranked suggestions can come from themeTargetHeuristics.runAndRecordThemeTargetProbe which already produces candidate signals — the radial menu's Apply tab is a thin re-presentation of those candidates.

Sphere shader uniforms — the bridge to the design tweaks

The current NodeSphereProgram ships a static fragment shader (light direction is hardcoded vec3(-1, -1, 1); rim direction is vec2(1, 1); specular exponent is 32). The design's three new tweaks (nodeHum, nodeFlowSpeed, nodeGlow) need to feed the shader as uniforms: 

// proposed: NodeSphereProgram.ts — add three uniforms
const SPHERE_FRAGMENT_SHADER = `
precision mediump float;
varying vec4 v_color;
varying vec2 v_position;
uniform float u_time;           // from rAF
uniform float u_hum;            // nodeHum (0–2)
uniform float u_flowSpeed;      // nodeFlowSpeed (0–2)
uniform float u_glowStrength;   // nodeGlow (0.2–2)

void main() {
  vec2 center = vec2(0.5, 0.5);
  float dist = distance(v_position, center);
  float radius = 0.5;
  float alpha = 1.0 - smoothstep(radius - 0.02, radius, dist);
  if (alpha < 0.01) discard;

  // existing: phong specular, rim, glow falloff …

  // new: hum — radial breathe synchronized to u_time
  float humPulse = 0.5 + 0.5 * sin(u_time * u_hum);
  vec3 humTint = v_color.rgb * (0.20 * humPulse);

  // new: flow — interior rotating ellipse using u_time * u_flowSpeed
  float angle = u_time * u_flowSpeed;
  vec2 flowed = vec2(
    cos(angle) * (v_position.x - 0.5) - sin(angle) * (v_position.y - 0.5),
    sin(angle) * (v_position.x - 0.5) + cos(angle) * (v_position.y - 0.5)
  );
  float flowMask = smoothstep(0.05, 0.0, abs(flowed.x * 1.4));
  vec3 flowTint = v_color.rgb * flowMask * 0.45;

  // glow strength scales the existing falloff
  vec3 glowColor = v_color.rgb * 0.5 u_glowStrength * glow;

  vec3 finalColor = v_color.rgb + glowColor + vec3(specular) + vec3(rimLight)
                  + humTint + flowTint;
  gl_FragColor = vec4(finalColor, v_color.a * alpha);
}
`;

The above is illustrative — the precise math wants tuning against the design's screenshots — but the shape (three uniforms, u_time driven by requestAnimationFrame) is the right pattern. SigmaGraphView would set these uniforms once per frame from the corresponding settings values.

v86c · Tile System

Per-Section Tear-Off + Snap + Groups

Replaces Tile.tsx's tab-level model with the design's section-level model, snap grid, and group machinery. The biggest piece in the integration.

Provider + state

Floating tile + snap

  • Add findSnap that checks distance to the 16px grid and to all other tiles' edges; resolve at onMouseUp.
  • Snap state lives in the tile entry's x/y coordinates; no separate snap-target state.
Groups
  • computeGroups recomputed on every layout change; result is ephemeral, not persisted.
  • Group bar is a sibling DOM element, position computed from top-row tiles' rectilinear hull.
  • Group outline is a single SVG polygon path traced over the rectilinear hull (per the user's BIG RULE — no bounding-box rectangle).
  • Per-tile slim strip with grip handle that, on drag, pulls the tile out of the group (un-snap → drift to cursor).
Pin/dock zones (deferred)
  • Out of scope for first landing. Document as a planned follow-up handle.
  • Consider snapping to the right edge of the canvas as a degenerate case in findSnap early so adding dock zones later is additive.
Stopping point

Tiles snap to grid and to each other; two snapped tiles form a group with a custom-shape outline and a top-row-width-only group bar. Layouts persist across reloads via useSettingsStore.

Closing note

Three of the conflicts in this report (the empty files, the stale registry, the Settings tab) are pre-existing — they would be true whether or not the design integration ever happened. Use the pause point as the natural moment to clean them up alongside the new work, rather than letting them propagate into the post-design codebase.

Everything else is the consequence of doing real design work against a real codebase: the design was opinionated and the code is opinionated, and the seams between them are exactly where the opinions disagree. None of those seams require violence to either side. They require ordered, deliberate work.
